> 记录我在 AI 眼镜管理平台上的一次联调排障，以及用户标识（userTag）功能的落地。踩了配置、模板、认证三个坑，也澄清了两个"看起来像 bug、其实是设计"的机制。写下来，给自己留个复盘。

## 项目背景

AI 眼镜管理平台，技术栈：

- 前端：Vue3 + Vite + TypeScript（`aiglasses-web`）
- 后端：Spring Boot + yudao 风格框架（`backend`，模块化多 Maven 工程）
- 数据库：PostgreSQL（远程环境）

## 一、发生了什么

前端连不上后端。

浏览器控制台里报错刷屏，HTTP 和 WebSocket 同时报 `ERR_CONNECTION_REFUSED`。我第一反应是代码写错了，准备回头翻逻辑。

后来查下来，错得简单到有点尴尬：**前端配置指向的是一台早就不跑服务的旧机器。**

## 二、排查链路：我是怎么一步步缩小范围的

### 第一步：先分清是哪一类报错

一开始我差点直接去翻代码。停下来之后，我先做了一件事：**把报错分类**。

"后端没反应"这件事，其实要拆成好几种完全不同的情况：

| 报错 | 含义 | 结论 |
|---|---|---|
| `ERR_CONNECTION_REFUSED` | TCP 连接被拒绝，端口上没有进程在监听 | 后端没起 / 起在别处 |
| `404` | 请求到了，但路径不存在 | 接口路径不匹配 / 旧代码 |
| `500` | 请求到了，后端处理异常 | 看日志堆栈 |
| CORS / timeout | 中间链路问题 | 代理、跨域、防火墙 |

这个分类的价值在于，**光看报错就能排除掉一大片无关的排查方向。**

我当时是 HTTP 和 WebSocket 同时报 `ERR_CONNECTION_REFUSED`。

两个协议、同一个地址，都返回"连接被拒"。这说明目标地址的 48080 端口**根本没有服务在监听**。如果后端代码有问题，报的应该是 `500` 而不是这个。

到这里，我的结论变成了：不是代码问题，是"服务没在预期的地方"。

### 第二步：确认服务到底在哪

既然是"服务不在预期的地方"，那就去找服务实际在哪。两步：

```bash
netstat -ano | grep 48080
# TCP  0.0.0.0:48080  LISTENING  23288   ← 后端在本机正常监听

ipconfig
# IPv4: 192.168.1.228                      ← 本机 IP 是 .228，不是 .170！
```

后端其实一直在跑，就在本机，端口也对。

那问题就只剩一种可能：**前端连的地址不对。**

### 第三步：核对前端配置

打开前端 `.env.local`，果然：

```
VITE_BASE_URL='http://192.168.1.170:48080'
```

`.170` 是另一台机器，可能是以前部署后端的机器，服务早停了。把配置改成 `.228`，联调恢复。

### 我的错误

看到 `ERR_CONNECTION_REFUSED` 的第一反应是想翻代码，这是方向性误判。

正确的顺序应该是：**先分类报错 → 确认服务在哪 → 最后才怀疑代码。** 我差点把这个顺序走反了。

## 三、第二个坑：Excel 导入"没报错，但数据没进去"

加完"用户标识"（userTag）字段后，导入 Excel 全程不报错，但这一列的数据没落库。

这种"静默失败"比报错还难查。我的排查思路是**沿着数据流一层一层往下确认，最终排除代码**：

1. VO 注解：`UserImportExcelVO` 已加 `@ExcelProperty("用户标识")` ✓
2. 模板生成：`get-import-template` 用 `ExcelUtils.write(..., UserImportExcelVO.class, ...)` 反射注解自动生成表头，新模板应包含该列 ✓
3. 解析：`ExcelUtils.read(file, UserImportExcelVO.class)` 按表头名匹配列 ✓
4. 落库：`BeanUtils.toBean(importUser, AdminUserDO.class)` 同名字段拷贝 ✓

四步走下来，代码这一侧每一环都是对的。

到这里我停了一下，因为链路里有一个我一直默认、却没去验证的前提：**"用户导入的那个 Excel，真的是我想象的那份"。**

最后问题就出在这里。EasyExcel 是按表头名匹配的：

```
旧模板没有"用户标识"列 → 字段解析成 null → 静默不录入 → 全程无报错
```

**用户手里的是加字段之前下载的旧模板。** 代码没问题，是输入数据错了。

### 我的教训

两条：

1. 加了字段**必须重新下载模板**——"不报错但数据缺失"是最容易踩的坑。
2. "静默失败"比"报错失败"难查十倍。排查时**优先确认输入数据到底有没有被解析到**，而不是闷头查代码。代码往往是对的，错的是你喂进去的东西。

## 四、两个"看着像 bug，其实是设计"的机制

排查过程中，我两度以为代码写崩了，弄清之后发现都是框架的默认设计。

### 1. 删了用户，数据库里怎么还有？

恐慌了两秒，才反应过来是**逻辑删除**。框架全局配置：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-value: 1   # 删除 = UPDATE deleted = 1，而不是 DELETE
```

所以"删除用户"实际执行的是 `UPDATE ... SET deleted = 1`，查询时框架自动追加 `deleted = 0` 条件。防误删、可恢复，是长期维护系统的标准做法。

### 2. 用户 ID 为什么一直自增、不复用？

主键是**雪花算法**，应用层生成 19 位趋势递增数字：

```java
@TableId(type = IdType.ASSIGN_ID)
private Long id;
```

因为用户 ID 被几十张关联表引用，**复用会导致数据串号**。删除后不复用是正确设计，逻辑删除的记录也不占序列，无需清理。

## 五、userTag 功能的完整落地

排障只是前半场，真正要交付的是"用户标识"字段从入参到落库完整打通。

### 数据层

`AdminUserDO` 加字段，配套迁移 SQL：

```java
/** 用户标识（逗号分隔的标签串，如 expert,common） */
private String userTag;
```

```sql
alter table system_users add column user_tag varchar(255) default '';
comment on column system_users.user_tag is '用户标识';
```

### VO 三件套

入参 `UserSaveReqVO`、出参 `UserRespVO`、导入 `UserImportExcelVO` 三处同步加字段，创建/编辑/查询/导入接口自动全链路支持：

```java
// UserImportExcelVO
@ExcelProperty("用户标识")
private String userTag;
```

### 导入密码策略

原来的逻辑是：无论模板填不填密码，一律覆盖成系统初始密码。这对"更新用户"很不友好。改成：

| 场景 | 行为 |
|---|---|
| 新建 + 模板密码为空 | 用系统初始密码 |
| 新建 + 模板填了密码 | 用模板密码 |
| 更新 + 模板密码为空 | 保持原密码（updateById 忽略 null） |
| 更新 + 模板填了密码 | BCrypt 加密后更新，避免明文落库 |

### 框架层一个增强

给 Jackson 开了单值兼容数组，让 `postIds` 传 `1`（而不是 `[1]`）也能正确反序列化，兼容设备端和第三方"单值当数组传"的习惯：

```java
.featuresToEnable(DeserializationFeature.ACCEPT_SINGLE_VALUE_AS_ARRAY)
```

## 六、一个我自己造成的坑：git 里的 token

推送代码的时候报：

```
remote: Https克隆账号或密码错误
fatal: Authentication failed
```

排查后发现，remote URL 里**硬编码了一个内嵌 token**：

```
https://oauth2:pt-xxxxx@codeup.aliyun.com/.../backend.git
```

这个坑是我自己埋的。

个人访问令牌（PAT）有过期时间，过期就报"账号或密码错误"。处理三步：移除 URL 里的 token、清理凭据管理器旧条目、重新生成令牌。

### 我的教训

虽然是我自己的操作失误，但这件事值得记下来：

1. **token 不要硬编码在 URL 里**。既会过期失效，又有泄露风险（`git config` 明文可见）。
2. **敏感凭据应该交给系统凭据管理器托管**，而不是写死在配置或 URL 里。

## 七、这次学到了什么

把这次的经验沉淀成几条：

1. **排障先分层**：请求到没到后端（`ERR_CONNECTION_REFUSED` 就是没到）→ 路径对不对（`404`）→ 后端有没有报错（`500`）→ 数据层。从报错类型定位到层，而不是乱枪打鸟。
2. **"没报错但结果不对"，先怀疑输入侧**：旧模板、旧缓存、旧配置，十有八九是它们。
3. **框架默认行为先确认再质疑**：逻辑删除、雪花 ID 都是设计，不是 bug。
4. **敏感凭据交给凭据管理器**：token、密码这类别硬编码在配置或 URL 里，既会过期，又会泄露。

下次再遇到"后端没反应"，我会先敲 `netstat` 和 `ipconfig`，而不是先翻代码。
